# Luxor — Аудит проекта

Дата: 2026-07-03
Область: `luxor/` (Tauri 2 + Vite + React 19 + Rust workspace) и корневой Next.js-проект.

Проверено: typecheck, ESLint, 327 unit-тестов (0 fail), prod-сборка (7.3s, dist 3.2MB),
аудит зависимостей, IPC-поверхность (`#[tauri::command]`), core-модули Rust
(`fsx`, `pty`, `secrets`, `gitx`, `httpx`, `launcher`, `redact`, `webhook`, `search`),
фронтовый мост `ipc.ts`, система плагинов, жизненный цикл панелей, паттерны
производительности и доступности. Rust проверен чтением кода (`cargo` в песочнице недоступен).

---

## 1. Сильные стороны

- Строгий `tsconfig` (strict, noUnusedLocals), ноль `: any` в исходниках.
- `dangerouslySetInnerHTML` в EditorPanel санитизируется через DOMPurify.
- Узкие Tauri-capabilities: только окна/диалоги/нотификации, без fs/shell из фронта.
- Встроенный браузер — отдельный child webview **без capabilities**: удалённый контент
  физически не достаёт до IPC. Правильная архитектура.
- Git через `git2` (libgit2), не через shell — инъекции аргументов исключены;
  токены из OS keychain через credential callbacks.
- Secrets — только OS keychain, валидация имён аккаунтов, `exists()` без выдачи значения.
- SQLite-вьюер: `quote_ident` + параметризация + валидация таблиц/колонок против реальной
  схемы, `escape_like` для фильтров.
- PTY: coalescing вывода (8ms/64KB), ровно один `Exited` через AtomicBool,
  обработка poisoned locks без паник.
- `redact.rs` маскирует Bearer/ghp_/sk_-токены в логах; в `httpx` есть SSRF-guard с тестами.
- Хорошая база стабильности: `AppErrorBoundary` + `PanelErrorBoundary` (изоляция падений
  по панелям), `lazy()`/`Suspense` для code-splitting, 41 race-guard
  (AbortController / stale-флаги) в 7 панелях.
- `search.rs` ограничивает результаты (`max_results.clamp(1, 5000)`).
- Code-splitting сделан грамотно: xterm, codemirror (+ языки по отдельности), dockview,
  react, иконки, i18n — отдельными чанками.
- 42 файла тестов, включая security-тесты (`../../etc/passwd` в тестах `is_within_root`).

## 2. Безопасность

### 2.1 [P0] FS-команды не ограничены project root — главная дыра

`fs_write_text`, `fs_delete(recursive: true)`, `fs_rename`, `fs_copy`, `fs_read_text`,
`db_query(allow_write: true)` принимают **произвольный путь** с фронтенда без проверок.
Функция `is_within_root()` написана и протестирована, но подключена **только к `search.rs`**.
Заявленный «restrict file operations to the project» режим для мутирующих операций
не существует. Любой XSS в webview = чтение/запись/рекурсивное удаление всего диска.

**Фикс:** `PathGuard` в Tauri state — все мутирующие FS/DB-команды валидируют путь через
`is_within_root` против набора открытых project roots, с канонизацией симлинков
(не только лексической). Опционально настройка «разрешить вне проекта» с явным confirm.

### 2.2 [P0] Верификация плагинов — FNV-1a вместо криптохэша

`plugins.ts`: манифест документирует `contentHash` как "Expected SHA-256", а фактически
считается **FNV-1a 64-bit** (`fnv1a64Hex`) и сверяется с `TRUSTED_HASHES`. FNV — не
криптографический хэш: коллизию под доверенный хэш можно сконструировать. Плагины
исполняются в том же webview-контексте с полным IPC — вредоносный плагин получает
дыру из 2.1 целиком.

**Фикс:** настоящий SHA-256 (`crypto.subtle.digest` на фронте + `sha2` в Rust),
либо изоляция плагинов в sandboxed iframe без IPC, как задокументировано.

### 2.3 [P0] PTY `autorun` — потенциальный RCE при открытии чужого проекта

`SpawnOptions.autorun` пишет команды прямо в shell при спавне терминала (layout preset
autorun). Если пресеты читаются из конфига внутри открываемого проекта — открытие
склонированного репозитория выполняет произвольные команды.

**Фикс:** проверить источник пресетов; если проектный — allowlist и/или confirm-диалог
перед autorun.

### 2.4 [P0] HtmlPreviewPanel — локальный HTML без sandbox + `assetProtocol.scope: ["**"]`

Комментарий в коде: "no iframe sandbox restrictions on local files". В сочетании с
`assetProtocol.scope: ["**"]` и `frame-src ... asset:` любой HTML-файл с диска рендерится
с JS и может читать **любые файлы диска** через asset URLs.

**Фикс:** сузить `assetProtocol.scope` до app-data + открытых project roots; добавить
`sandbox` атрибут в preview-iframe.

### 2.5 [P0] Уязвимые зависимости (2 moderate)

- `dompurify <= 3.4.10` (GHSA-cmwh-pvxp-8882, prototype pollution через `setConfig()`) —
  в `luxor/` и в корне. Обновить до >= 3.4.11.
- `postcss < 8.5.10` (XSS через `</style>`) — в корне. Обновить до >= 8.5.10.

### 2.6 [P0] Updater без ключа подписи

`tauri.conf.json`: `updater.active: true` + `createUpdaterArtifacts: true`, но
`"pubkey": ""`. Авто-обновления либо сломаются при сборке, либо будут без верификации.

**Фикс:** `tauri signer generate`, pubkey в конфиг, секретный ключ — в CI-секреты;
либо `active: false` до готовности релизной инфраструктуры.

### 2.7 [P1] SSRF-guard выключен по умолчанию

`httpx`: guard есть, но `Defaults to false`. HTTP-панель по умолчанию ходит в
localhost/private-сети. Минимум — предупреждение в UI при выключенном guard.

### 2.8 [P1] CSP широковата

`frame-src ... https: http:` — для in-app браузера объяснимо, но стоит пересмотреть
вместе с 2.4.

## 3. Производительность

### 3.1 [P1] Нет виртуализации списков

Ни одной виртуализации в проекте (`react-window`/`virtua`/`useVirtualizer` — 0 вхождений).
22 `.map()`-рендера в FilesPanel/GitPanel/SearchPanel. Дерев�� файлов, git log и
результаты поиска (до 5000 записей с бэкенда) рендерятся целиком в DOM.
На больших репозиториях — фризы UI.

**Фикс:** виртуализировать FilesPanel (плоский список видимых узлов уже есть — `rows`),
SearchPanel results, GitPanel log. Рекомендация: `virtua` (лёгкая, ~3KB).

### 3.2 [P1] Почти нет мемоизации тяжёлых компонентов

`React.memo` только в 4 файлах на ~60 компонентов панелей. Строки дерева/списков
перерендериваются при каждом изменении selection/expand. Вместе с 3.1 — основной
источник jank.

**Фикс:** после виртуализации обернуть row-компоненты в `memo` со стабильными пропсами.

### 3.3 [P2] Нет FS-watcher — панели работают на поллинге/ручном refresh

В Rust-core нет `notify`-watcher. BrowserPanel поллит bounds каждые 250ms,
HtmlPreviewPanel — autoRefresh интервалом. Поллинг жрёт CPU в фоне.

**Фикс:** `notify` crate + событие `fs:changed` по открытым roots; заменить
интервальные поллинги на события. Для BrowserPanel — пересчёт bounds по
ResizeObserver/dockview events вместо таймера.

### 3.4 [P2] Бандл: главные чанки

xterm 426KB, codemirror 420KB, main 235KB, dockview 207KB (до gzip). Сплит уже хороший;
возможный выигрыш — грузить cm-lang-* только по факту открытия файла данного языка
(проверить, так ли сейчас) и отложить xterm до первого открытия терминала.

## 7. CI/CD, тесты, i18n, темизация (аудит 4)

### 7.1 [P0] CI frontend-job сломан: `npm ci` без package-lock.json

`.github/workflows/ci.yml` использует `actions/setup-node` с `cache: npm` и `npm ci`,
но в репозитории только `bun.lock` (package-lock.json нет). `npm ci` падает без
lockfile — весь frontend-job CI (typecheck/lint/build на 3 ОС) не работает.
При этом visual-regression.yml корректно использует `setup-bun` + `bun install`.

**Фикс:** перевести ci.yml на `oven-sh/setup-bun@v2` + `bun install --frozen-lockfile`
(как в visual-regression.yml), команды через `bun run`.

### 7.2 [P1] Все 20+ панелей без тестов

42 тест-файла покрывают только `src/lib` (чистая логика). Ни одна панель не имеет
тестов: ActivityPanel, AgentsPanel, AnalyticsPanel, BrowserPanel, DbPanel, DiffPanel,
DockerPanel, EditorPanel, FilesPanel, GitPanel, HtmlPreviewPanel, HttpPanel,
LauncherPanel, SearchPanel и др. Вся интеграционная логика (IPC-вызовы, race-guards,
cleanup) не проверяется — регр����ссии в панелях ловятся только вручную.
Rust покрыт хорошо (240 тестов).

**Фикс:** Testing Library + мок `ipc.ts`; в первую очередь — FilesPanel, GitPanel,
SearchPanel (самые сложные state-машины). Smoke-тест «панель рендерится и не падает»
для всех остальных.

### 7.3 [P1] Visual regression: флаки-запуск dev-сервера

`vite --port 5173 &` + `sleep 3` + один curl — если Vite стартует дольше 3с, job
падает ложно. Заменить на wait-on/retry-цикл до готовности порта.

### 7.4 [P2] Hotkeys: нет детекции конфликтов и системных перехватов

`hotkeys.ts` — редактируемый реестр без проверки дубликатов: пользователь может
назначить один чорд на два действия, победит порядок обработки. `Ctrl+W` (закрыть таб)
конфликтует с закрытием окна браузерного webview на некоторых платформах. macOS:
`metaKey` маппится в "Ctrl" (осознанно, отображение отличается) — но labels экшенов
захардкожены на английском и не проходят через `t()`.

**Фикс:** валидация уникальности чордов в настройках + подсветка конфликта;
labels через i18n.

### 7.5 [P2] i18n: только en/ru, локаль определяется, но архитектура не расширяема

`t(key, english)` с inline-английским — простой и быстрый паттерн (RU-словарь 1078 строк
грузится лениво — отлично), но добавление третьего языка потребует переезда. ОК как
осознанный трейдофф; зафиксировать решение в доках.

### 7.6 [P2] 66 захардкоженных цветов в TSX мимо темы

`#hex`/`rgb()` прямо в компонентах — тёмная/светлая тема в этих местах не работает
или требует ручной синхронизации. Вынести в CSS-переменные темы (`src/styles.css`).

### 7.7 Позитив (аудит 4)

- CI: Rust-матрица на 3 ОС с fmt + clippy `-D warnings` + тестами — образцово.
- Visual regression на PR через Playwright — редкая и полезная практика.
- i18n: лениво загружаемый RU-словарь вне критического пути старта.

## 8. Конкурентность, поток данных, целостность (аудит 5)

### 8.1 [P1] Редактор не детектит внешние изменения файла — риск потери данных

`EditorPanel` при сохранении (включая **autosave с дебаунсом 2с**) вызывает
`fs_write_text(path, content)` без проверки mtime/версии. Сценарий потери данных:
файл открыт в редакторе → внешнее изменение (git checkout/pull, форматтер, другой
редактор) → autosave срабатывает по dirty-состоянию → **внешние изменения молча
перезаписаны** старым буфером. Watcher'а нет (см. 3.3), «file changed on disk»
диалога нет.

**Фикс:** запоминать mtime при чтении; в `fs_write_text` добавить опциональный
параметр `expected_mtime` — при расхождении возвращать конфликт, показывать диалог
«Файл изменён на диске: перезаписать / перечитать / сравнить». Синергия с FS-watcher.

### 8.2 [P1] Блокирующие вызовы внутри async-команд (starvation tokio)

Heavy-операции (`gitx.rs`: `std::fs::read`, git2 — весь libgit2 синхронный;
`fsx.rs`: рекурсивный обход/удаление) вызываются напрямую из `pub async fn`
команд — на весь src-tauri всего 8 `spawn_blocking`. Длинный `git_log` по большому
репо или рекурсивное удаление занимает поток tokio-раннера: параллельные IPC-команды
(включая лёгкие) деградируют, UI «подвисает» на операциях.

**Фикс:** обернуть git2- и тяжёлые FS-вызовы в `tauri::async_runtime::spawn_blocking`.

### 8.3 [P2] Keychain-команды синхронные — блокируют main thread

`git_token_set/delete/exists` — sync `pub fn` (в Tauri выполняются на main thread).
Доступ к OS keychain может блокироваться на секунды (разблокировка связки ключей,
системный промпт) — фризит весь UI. Перевести на async + spawn_blocking.

### 8.4 [P2] 17 неогороженных `JSON.parse` на localStorage-данных

35 вызовов `JSON.parse` во фронте, только ~18 внутри try/catch. Повреждённое
значение в localStorage (частичная запись, ручное редактирование, смена схемы) —
и модуль падает при старте до ErrorBoundary. Нужен хелпер `safeParse<T>(raw, fallback)`
+ zod/валидация для критичных структур (layout, настройки).

### 8.5 Позитив (аудит 5)

- **`atomic_write` образцовый:** temp-файл в той же директории + rename (атомарность
  на том же fs), сохранение unix-прав, follow symlink к цели, uuid-имена tmp. Покрыт тестами.
- **Телеметрия полностью локальная:** SQLite `local_stats.db`, без сетевых отправок;
  опция маскирования — пути проектов хранятся как SHA-256. Приватность соблюдена.
- **Docker через `Command::new("docker")` с args-массивом** — без shell-интерполяции,
  инъекции аргументов исключены.
- **Все heavy FS/git/DB-команды объявлены async** — не блокируют main thread
  (проблема только в starvation tokio, см. 8.2).
- `dockStore` обрабатывает ошибки загрузки пресетов с тостом, не падает.

## 9. Контракт IPC, зависимости, мёртвый код (аудит 6)

Сверены все 197 зарегистрированных Rust-команд против 195 уникальных `invoke()`-вызовов
из TypeScript; проверены `bun outdated`, event-контракт и стартовый путь.

### 9.1 [P1] Сломанная фича: `docker_exec` вызывается, но команды в Rust нет

`src/lib/ipc.ts:637` → `dockerExec()` инвокает `"docker_exec"`, используется в
`DockerPanel.tsx:89` (диалог exec в контейнере). Команды `docker_exec` **не существует**
ни в `commands/extras.rs`, ни где-либо в src-tauri — в `generate_handler` она не
зарегистрирована. ��аждый вызов exec из Docker-панели падает в рантайме
("command docker_exec not found"). Тестов на панели нет (7.2), поэтому баг не пойман.

**Фикс:** реализовать `docker_exec` в Rust (через `Command::new("docker")` c
args-массивом, как остальные docker-команды) или убрать exec-UI из DockerPanel.

### 9.2 [P2] Контракт IPC ничем не защищён

Дрейф TS ↔ Rust (как в 9.1) обнаруживается только в рантайме: имена команд — строки,
типы аргументов/ответов дублируются вручную в `ipc.ts`. 197 команд — поверхность
большая. Варианты: кодоген (tauri-specta) или хотя бы CI-скрипт, сверяющий список
`invoke("...")` против `generate_handler`.

### 9.3 [P2] Зависимости: dockview отстаёт на 3 мажора, xterm на 1

- `dockview` 4.13.1 → 7.0.2 — ядро всего layout-а; апгрейд рискованный, но чем
  дольше откладывать, тем дороже. Минимум — зафиксировать решение и следить за фиксами.
- `@xterm/xterm` 5.5.0 → 6.0.0 (+addon-fit, addon-webgl мажоры).
- Остальное — патчи/минорки (codemirror, tauri api), можно обновить безопасно.

### 9.4 Мёртвый код: минимальный

Из 197 команд не вызываются с фронта только 4 (`latest_versions` — на деле
зарегистрирована и, вероятно, вызывается по-другому; `push_critical`,
`spawn_background`, `open_new_window`, `new` — внутренние/служебные вызовы из Rust).
Реального мёртвого кода в IPC-слое почти нет — хороший показатель.

### 9.5 Позитив (аудит 6)

- Единая обёртка `invoke()` в `ipc.ts` со structured-логированием всех падений IPC.
- `main.tsx`: perf-марка первой строкой, некритичная инициализация вынесена

- Покрытие IPC-поверхности фронтом 195/197 — контракт почти полностью живой.

## 10. Жизненный цикл приложения, launcher, agents, CSS (аудит 7)

Проверены: launcher/внешние программы, agent-router, окно/трей/выход, pid-файл и
CLI-очередь, конфиг-персистенция, упаковка (bundle/updater), CSS-архитектура.

### 10.1 [P1] Updater активен с пустым pubkey и живым endpoint — подтверждено

Уточнение к 2.6: endpoint настроен (`github.com/luxor-app/luxor/releases/.../latest.json`),
`active: true`, Windows `installMode: passive` (без подтверждения пользователем),
`pubkey: ""`. Если сборка вообще пройдёт — это канал доставки неподписанных
обновлений. Приоритет фикса поднят: ключи или `active: false` до релизной инфраструктуры.

### 10.2 [P2] Нет GUI single-instance guard — риск гонок за config/telemetry

Pid-файл обслуживает только CLI-сценарий (`luxor .` кладёт запрос в очередь,
staleness через sysinfo — сделано грамотно). Но **прямой повторный запуск GUI не
блокируется**: два инстанса делят `config.toml` (atomic write спасает от порчи, но
last-write-wins молча теряет настройки) и `local_stats.db` (SQLite-блокировки →
ошибки записи телеметрии). Фикс: `tauri-plugin-single-instance` + фокус существующего окна.

### 10.3 [P2] CLI-запросы опрашиваются поллингом «каждые несколько секунд»

`cli_poll_requests` поллится с фронта — третий поллинг-цикл в системе (после
bounds-poll BrowserPanel и отсутствия FS-watcher). `luxor .` из терминала открывает
проект с задержкой до интервала поллинга. Фикс: Rust-сторона пишет запрос и сразу
эмитит событие — фронт слушает вместо опроса.

### 10.4 [P2] Упаковка: нет подписи macOS/Windows

`bundle.targets: "all"`, `signingIdentity: none`, секции notarization нет. Для
распространения вне dev: Gatekeeper заблокирует .app, SmartScreen — .exe.
Зафиксировать план подписи до первого публичного релиза (вместе с 10.1).

### 10.5 [P2] CSS-монолит: 2445 строк, 57 `!important`

Один `styles.css` на всё приложение + панельные стили. 57 `!important` — признак
войн специфичности (в основном перекрытие dockview/xterm). Позитив: z-index
дисциплинирован (максимум 10, 4 уникальных значения). Фикс: распил по слоям
(`@layer base/vendor-overrides/components`), сократить `!important`.

### 10.6 [P3] Каталог моделей agent-router захардкожен и устареет

`agentRouter.ts` — статические таблицы моделей/цен/приоритетов («claude-sonnet-4»,
«gemini-2.5-pro», costPer1K). Роутинг локальный (сам не ходит в сеть — хорошо),
но таблицы будут дрейфовать от реальности. Вынести в конфиг/обновляемый JSON.

### 10.7 Позитив (аудит 7)

- **Выход без осиротевших процессов:** `cleanup_before_exit` на `RunEvent::Exit` +
  `ExitRequested` глушит все PTY и снимает pid-файл — и при quit из трея, и при выходе.
- **Launcher безопасен:** чистые `SpawnPlan` (program+args+cwd) без shell-интерполяции,
  покрыт тестами, детект терминалов/IDE отделён от исполнения.
- **Config-персистенция:** атомарная запись + сохранение неизвестных TOML-ключей
  (forward-совместимость со старыми версиями — протестировано).
- **Трей продуман:** одноразовый хинт «приложение живо в трее», watchdog попапа через
  generation counter (ровно один жив), отдельная 32px-иконка для чёткости рендера.
- **CLI staleness:** проверка живости pid через sysinfo, а не слепое доверие файлу.

## 11. Webhook, лимиты ресурсов, буферы, сборка (аудит 8)

Проверены: webhook.rs (Slack/Telegram digest), notify.ts, httpx-лимиты, лимиты
чтения файлов/blame, рост логов и телеметрии, vite-конфиг прод-сборки, dispose-цепочка
терминала.

### 11.1 [P2] Telegram bot token утекает в текст ошибок

`send_telegram` встраивает токен в URL (`api.telegram.org/bot{token}/...` — так
устроен Telegram API), но при сбое возвращает `Error::Http(reqwest::Error)`, чей
`Display` **включает полный URL с токеном**. Ошибка уходит в лог/тост фронтенда.
`redact.rs` маскирует Bearer/ghp_/sk_-паттерны, но не токен внутри telegram-URL.

**Фикс:** маппить reqwest-ошибку в собственную с вырезанным URL (или добавить
telegram-паттерн `bot\d+:[A-Za-z0-9_-]+` в redact) до возврата из `send_telegram`.

### 11.2 [P3] Digest в Telegram с `parse_mode: Markdown` — хрупкая отправка

Текст дайджеста содержит имена проектов/веток; спецсимволы Markdown (`_`, `*`, `[`)
в имени ломают парсинг на стороне Telegram → API возвращает 400 и весь дайджест
не доставляется. Использовать `MarkdownV2` с экранированием или слать plain text.

### 11.3 [P3] Webhook-креды не сохраняются — вводить заново каждый раз

Slack URL и Telegram token/chat живут только в `useState` панели AnalyticsPanel.
Безопасно (нигде не персистятся), но UX страдает: еженедельный дайджест требует
повторного ввода кредов. Если добавлять персистенцию — только через OS keychain
(механизм `secrets.rs` уже есть), не в config/localStorage.

### 11.4 Позитив (аудит 8) — лимиты ресурсов выдержаны системно

- **httpx:** стриминг тела с жёстким капом 2MB (не буферизует целиком), флаг
  `truncated`, таймаут clamp 1–120с.
- **fs-чтение:** превью с капом по байтам, peak memory ограничен независимо от
  размера файла; понятная ошибка «file too large».
- **git blame:** кап 20 000 строк с флагом truncated; `log`/`file_history` — limit.
- **Рост данных ограничен везде:** logBuffer капирован, activityLog — 300 событий,
  телеметрия — retention с rollup-агрегацией и удалением сырых интервалов.
- **vite prod:** sourcemaps выключены, target es2022, кастомный плагин
  `drop-cm-preload` против лишних prefetch-запросов CodeMirror.
- **Терминал:** полная dispose-цепочка (webgl-аддон с guard, link-provider, OSC,
  флаг `disposed` против пост-анмаунт колбэков); scrollback настраиваемый (деф. 10к).
- **Уведомления:** осознанная деградация WebView2 → plugin-notification → Web API,
  OS-нотификации только при скрытом окне, гейт через конфиг.
